# Объекты сцены: размещение, Z-order, клик-зоны, курсоры

Геометрия вскрыта в `ROBY.EXE` (`ImageBase 0x400000`): парсер `.SCN`
(`0x411d80`), `FonScript::Render` (`0x4165b0` — одна функция рисует **все**
спрайты), `Scene::ObjectAtPoint` (`0x4151a0`), `BuildDrawList` (`0x414860`).
`NGI32.DLL` даёт только «положить NGB в точку» (`ngiSetNgbOrigin`,
`vrtPutNgb`) — координатной логики там нет.

Глобальные константы сцен: `GridSize=(144,36)`, `ZPerGrid=8`. `GridShift`
**НЕ константа** — обычно `(46,-99)`, но `CAB_B1=(46,-97)`, `CAB_C2=(46,-94)`;
читать все шесть чисел (`LeftTopGrid`, `GridSize`, `GridShift`) из каждой `.SCN`.

## Сетка: клетка → экран

Сетка — обычная прямоугольная решётка `GridLength.x × GridLength.y` клеток
размера `GridSize`. `LeftTopGrid` — левый-верхний пиксель клетки (0,0).

```
corner(gx,gy) = LeftTopGrid + (gx*GridSize.x, gy*GridSize.y)      // угол клетки
anchor(gx,gy) = corner(gx,gy) + GridShift                        // якорь спрайта
экран         = anchor - scroll
```

`GridShift` **прибавляется один раз**, а не масштабируется по `gy`. Обратное
преобразование (пиксель → клетка, `0x40f20a`) инвертирует **corner**, без
`GridShift`: `gx = (px - LeftTopGrid.x) / GridSize.x` (усечение), затем кламп в
`[0, GridLength-1]`. Отладочная сетка `GridDebug` (`0x4145c7`) рисует ровно эту
решётку от `corner(0,0)` — `GridShift` в ней не участвует.

## Спрайты: полный холст на `anchor − Shift`

`FonScript::Render` кладёт спрайт так, чтобы **хотспот ролика** `Shift` лёг на
`anchor`, и блитит **весь холст** (кадры `.NGB` имеют `x0=y0=0`):

```
spriteOrigin = anchor(gx,gy) - Shift
пиксель холста (u,v) → экран (spriteOrigin.x + u, spriteOrigin.y + v)
```

`Shift` — origin из заголовка `.SCR` ролика (offset `0x18/0x1C`); `.SCR` там же
несёт размер холста (`0x10/0x14`). FonScript может переопределить `Shift`
собственным ключом `Shift x,y` (`.FS`, поле `+0x38/+0x3C`) — из всех роликов
так делает только `wave` (холст 640×480, `.SCR`-origin `(53,231)`, но `.FS`
задаёт `(60,195)`). Проверено побайтно: `palma (240,271)`, `crb (29,54)`,
`fire (90,227)`, `bgstone (92,43)`, `head (116,85)`, `RG_56 (57,62)` — все
совпадают со значением `.SCR`.

Никакого масштабирования холстов 640×480 ↔ 1024×768 нет: художник подбирал
`Shift` под клетку. Пример SCENA0 (`LeftTopGrid=(15,150)` ⇒
`anchor=(61+144·gx, 51+36·gy)`):

| объект | клетка | Shift | anchor | spriteOrigin | на экране (opaque) |
|---|---|---|---|---|---|
| palma | (2,3) | 240,271 | 349,159 | **109,−112** | 357,−22 … 563,306 |
| wave | (0,4) | 60,195 | 61,195 | 1,0 | 1,349 … 1024,399 |
| bgstone | (2,3) | 92,43 | 349,159 | 257,116 | 400,274 … 421,293 |
| Roby `head` | (3,4) | 116,85 | 493,195 | 377,110 | 493,195 … 553,315 |

Пальма даёт `spriteOrigin.y = −112`: её крона **штатно обрезается** верхом
игрового поля (как и фоновые деревья) — это не баг, не «чинить».

## Экран и скролл

Поверхность сцены — `640 × ScreenSize.y` (обычно 640×400; у `INT0..INT4`
объявлено `ScreenSize 640,480`). Всё ниже `ScreenSize.y` обрезается; под сценой
панель инвентаря `y=400..480` (`BAR.BAR: BarLTWH 0,400,640,80`).

Скролл включён по осям, где `ScreenSize > (640, 480)` (SCENA0 = 1024 шир. →
только горизонтальный). На входе в сцену
`scroll = (gx*GridSize.x − 320, gy*GridSize.y − 240)`, клампы: `<20 → 0`,
`> ScreenSize − 660 → ScreenSize − 640`. `ShiftScreen dx,dy` задаёт цель
скролла **в клетках** (`scroll += dx*GridSize`).

## Z-order

```
z = gy*ZPerGrid + ZCoord            (ZPerGrid=8; рисовать по возрастанию z)
```

`BuildDrawList` идёт `z = 0..40`: на каждом уровне сперва **персонажи**, затем
объекты — при равном `z` объект перекрывает персонажа. Хит-тест (`ObjectAtPoint`)
идёт по `z` сверху вниз (от 40): берётся верхний объект. `Shift char,Y,±1` в
циклах ходьбы меняет ряд **без** пересчёта `z` — поэтому циклы несут явный
`Set char,Z,n`.

## Клик-зона (ActiveZone)

`ActiveZone` в `.OB` хранится как есть `{x,y,w,h}` и привязана к **углу клетки**,
не к спрайту:

```
rect.xy = corner(gx,gy) + ActiveZone.xy - scroll
rect.wh = ActiveZone.wh
```

Ни `GridShift`, ни `Shift` не участвуют. (Совпадение зоны со спрайтом бывает
только когда `spriteOrigin = (0,0)`, т.е. `Shift = anchor` — так у многих
объектов, но не у пальмы.) У высоких объектов зона намеренно накрывает
кликабельную часть (ствол), а не весь спрайт.

Кликабельный бокс персонажа — отдельный, и он **использует** `GridShift`:
`charRect = anchor(gx,gy) + LookBox(l,t,r,b)` (Roby `LookBox=-10,-10,50,50`).

## Персонаж

Рисуется тем же `FonScript::Render`: **полный холст на `anchor − Shift`**, где
`Shift` — origin ролика (`head=(116,85)`). Кадры кропить/пинить к «ногам» не
нужно: линия ног сама ложится на `corner.y + 21` для стандартного героя высотой
120 px, а под-клеточное смещение шага «зашито» художником в холсты циклов —
поэтому цепочка ходьбы стыкуется без швов.

## Классы анимации

- **Статичные** (1 кадр): bgstone, coco, palma, sstone, woods, clay.
- **Зациклённые** (последний кадр без терминальной команды → возврат к 0):
  fire (3 к.), crb (4 к.), wave (5 к.), sound (переигрывает звук по таймеру).
- **One-shot** (последний кадр несёт `DelObject`/`GoScene`/`ShowChar`): smoke
  (35 к., самоудаляется), fraskcon, rotalk — скриптовые события.

Правило: нет терминальной команды в последнем кадре — зациклить; иначе один раз.
`Delay` брать по модулю.

## `ObjectList`: читать по полям, а не по числам

Строка списка — `имя,gx,gy[,*]`, и разбирать её нужно **по полям**. Соблазн
выбрать из строки все числа регуляркой заканчивается плохо: у трети объектов
цифра в самом имени (`br0`, `bt3`, `map1`, `iva0`, `wave2`), и она становится
первой «координатой». В нашем ремейке этот баг сдвигал клетки **144 объектов
из 412** — в частности бревно `br0` в SCENA4 объявлено в `(2,1)`, а читалось
как `(0,2)`, и его доска перерезала героя.

## `ActiveZone`: их может быть несколько

`.OB` может объявить **массив** клик-зон, по строке на каждую (движок держит
`+0x90` массив по 16 байт и счётчик `+0x94`). Пример — `SCENA4/BR0.OB`:

```
ActiveZone  100,-30,80,33;
            180,-45,90,38;
```

Первая зона накрывает ствол, вторая — доску на нём. Если хранить одну, объект
теряет половину своей кликабельной площади.

## `ObjectList`: флаг присутствия

Пятый токен строки `ObjectList` (`*`) — флаг «объект есть на старте» (`+0x98`),
а не подсказка рендера. Беззвёздочные объекты появляются только после
`CreateObject scene,obj,Roby,dx,dy` (ставится в клетке персонажа + смещение) —
поэтому объявленная клетка такого объекта (напр. `smoke`) не совпадает с местом,
где он в итоге виден.

Проверка по данным: **у каждого** беззвёздочного объекта есть вызовы
`CreateObject`, называющие его (`gorght` 2, `goleft` 5, `gocanib` 2, `canib` 1,
`outdoor` 6) — то есть флаг это действительно квестовый гейт, а не «скрыть
спрайт». `BEGIN.BGI` (побайтово равен `START.SAV`) несёт то же значение как
стартовое состояние мира.

## Выходы из локации

`GOLEFT.OB` / `GORGHT.OB` — **обычные объекты, перечисленные в `ObjectList`**
со своими клетками и флагом присутствия, как всё остальное. Клетки у каждой
сцены свои и константами не выводятся: `SCENA1 gorght` = (5,1), `SCENA2 goleft`
= (0,2), `SCENA3 gorght` = (6,3), `SCENA6 goleft` = (0,0). У них `FonScript NULL`
(спрайта нет), `Cursor 1/2` (стрелки ◄ ►), высокая `ActiveZone` вдоль края и
`Text` вида «Идти дальше?».

Флаг присутствия работает и для них: `SCENA0 gorght` объявлен без `*` и
открывается позже командой `CreateObject SCENA0,gorght,6,1` из скрипта SCENA2 —
то есть выход на восток закрыт до нужного места в сюжете. Создавать выходы
самостоятельно нельзя: это ломает и клетки, и гейт.

Тот же механизм у прочих переходов, которые не «влево/вправо»: `gocanib`
(SCENA2/SCENA4), `canib` (MAPSCR), `outdoor` (CAB_B6) — структурно те же
объекты с `FonScript NULL`, чей скрипт заканчивается `GoScene`, и все они
беззвёздочные с собственными `CreateObject`.

Клик по такому объекту запускает обычный скрипт действия (`ROHANGOL.FS`):
`Aproach Roby,goleft` — подход к краю, затем анимация ухода (`Ro_left.mv`),
реплика (`Text`), и в последнем кадре `GoScene`. Поэтому персонаж **всегда
что-то говорит перед уходом**; иногда `GoScene` обёрнут в `If`, и тогда
реплика есть, а перехода нет.

## Скрипты действий: `<персонаж><предмет><объект>`

Имя скрипта, который запускает клик, собирается из трёх частей по 2–3 буквы:

```
RO|FR  +  первые 3 буквы активного предмета  +  первые 3 буквы объекта
ROHANGOL = Roby + пустая рука (hand) + goleft
ROAXEWOO = Roby + топор (axe) + woods
FRHANBGS = Frid + пустая рука + bgstone
```

Объект берётся по **имени файла** `.OB`, а не по `ObjectName` внутри (у
`GORGHT.OB` внутри `gobanan`, но скрипт всё равно `…GOR`). Если для предмета в
руке скрипта нет — откат на `…HAN…`.

Скрипт может подменить себя вариантом: `SetCharVar rohangol,"r1hangol"` в
последнем кадре — символьная переменная называется **так же, как базовый
скрипт**, и при следующем клике движок берёт скрипт из неё. Так меняются
реплики при каждом уходе (`ROHANGOL` → `R1HANGOL` → …).

## Курсоры

Значения `Cursor` в `.OB`: 0..4 — навигационные, индекс в списке `BAR.BAR`
(`hand, adv1..adv4`). Графика — `RT_CURSOR` в `ROBY.EXE`, все 32×32:

| Cursor | Вид | Назначение |
|--:|---|---|
| 0 | рука | действие/осмотр по умолчанию |
| 1 | ◄ | выход влево (`goleft`) |
| 2 | ► | выход вправо (`gorght`) |
| 3 | ▲ | вход/вглубь |
| 4 | ▼ | выход вниз |

Плюс 33 курсора «предмет-в-руке» (по выбранному предмету инвентаря; список
`Items` в `BAR.BAR`). В контейнерах данных курсоров нет — только в `ROBY.EXE`.
