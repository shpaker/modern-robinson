# Кодеки `ngiUnpack`

Распаковка записей выполняется функцией `ngiUnpack` (`NGI32.DLL`, экспорт
`0x235D0` → ядро `sub_23740`). Метод берётся из поля `method` записи директории
и разбирается по битам:

| `method` | биты | кодек | что хранит | доля записей |
|---|---|---|---|---|
| `0x0000` | — | **raw** (memcpy) | `WAV`, редкие `NGB`/`COL`/`FAD` | 1 111 (4 %) |
| `0x0040` | `&0x1E0==0x40`, `&0x80==0` | **LZSS** (Okumura) | `FS`, `OB`, `SCN`, `CHR`, `LST` | 5 649 (20 %) |
| `0x0080` | `&0x80` | **LZHUF** (LZSS+Huffman) | `NGB`, `COL`, `SCR`, `FAD` | 21 066 (75 %) |
| `0x0100` | `&0x1E0==0x100` | графический вариант | 220 `NGB` + 6 `COL` + 1 `TXT` | 227 (0.8 %) |

Диспетчеризация в `sub_23740`: `method & 0x1E0` выбирает ветку, есть отдельная
таблица переходов по `0x23A10` (индексы в `0x23A28`). Ветки `0x40`/`0x80`
сходятся в общий декомпрессор `sub_26F4E`, который сам выбирает LZSS или LZHUF
по биту `0x80` входного флага.

---

## Метод `0x00` — raw

Данные лежат как есть, `usize == csize`. Просто копия байтов из блока.
Используется для звука: `WAVE.DAN` целиком состоит из RIFF/PCM `.WAV`
(проверено: `A01A.WAV` = PCM, mono, 22050 Hz, 16 бит, 1.25 с — открывается
системным плеером).

---

## Метод `0x40` — LZSS (Okumura)

Классический LZSS Харухико Окумуры. Реализация: `sub_26F4E`, ветка `bl & 0x80 == 0`
(`0x270E2`). Параметры сняты с дизассемблера:

- кольцевой буфер `N = 4096` байт, предзаполнен `0x20` (пробел);
- позиция записи стартует с `0xFEE` (`= N − F`, где `F = 18`);
- флаговый байт читается младшим битом вперёд: **бит 1 → литерал**,
  **бит 0 → ссылка** `(позиция 12 бит, длина 4 бита + 3)`;
- позиция в ссылке — **абсолютный** индекс в кольцевом буфере (0…4095).

```python
def lzss(src, out_size):
    N = 4096
    ring = bytearray([0x20]*N); pos = 0xFEE
    out = bytearray(); si = 0; flags = 0
    while len(out) < out_size and si < len(src):
        flags >>= 1
        if not (flags & 0x100):
            flags = src[si] | 0xFF00; si += 1
        if flags & 1:                          # литерал
            b = src[si]; si += 1
            out.append(b); ring[pos] = b; pos = (pos+1) & (N-1)
        else:                                  # ссылка
            lo = src[si]; hi = src[si+1]; si += 2
            p = ((hi >> 4) << 8) | lo          # 12-битная позиция
            length = (hi & 0x0F) + 3           # длина 3..18
            for _ in range(length):
                b = ring[p & (N-1)]; p += 1
                out.append(b); ring[pos] = b; pos = (pos+1) & (N-1)
    return bytes(out)
```

Результат — текст. Пример распакованного `BGSTONE.FS`:

```
ScriptName      DO NOTE;
MovieName       bgstone.mv;
Shift           92,43;
TotalFrames     1;

Frame 0,0;
Delay 71;

End;
```

## Метод `0x80` — LZHUF (LZSS + адаптивный Хаффман)

**Главный кодек игры** — 75 % записей, включая почти всю графику. Это канонический
LZHUF (Okumura/Yoshizaki): LZSS с адаптивным деревом Хаффмана поверх символов.
Реализация: `sub_26F4E`, ветка `bl & 0x80` (`0x26FA4`), декодер символа
`sub_26DCE`, инициализация дерева `sub_26D00`.

Константы подтверждены дизассемблером:

| Константа | Значение | Где в коде |
|---|---|---|
| `N` (кольцо) | 4096 | — |
| `F` (макс. длина) | 60 | `r0 = N−F = 0xFC4` (`mov ecx,0xFC4`) |
| `THRESHOLD` | 2 | длина = `c − 253` (`lea ebp,[ebx-0xFD]`) |
| `N_CHAR` | 314 | `256 − 2 + 60` |
| `T` (узлов) | 627 | `sub ebx,0x273` |
| `R` (корень) | 626 | — |
| `MAX_FREQ` | 0x8000 | реконструкция дерева |

Позиционные таблицы (`d_code`/`d_len`) вычисляются в BSS функцией `StartHuff`
(`sub_26D00`) из счётчиков `[1,3,8,12,24,16]` (d_code) и `[32,48,64,48,48,16]`
(d_len). **Важно: это НЕ канонические таблицы `lzhuf.c`** — `d_len` начинается
с `1,1,1…` вместо `3,3,3…`. Эталонный `lzhuf.c` даёт верный результат на
коротких потоках (мало матчей), но расходится на длинных. Нужны именно
NGI-таблицы + точный битридер: общий 32-битный аккумулятор, навигация дерева
берёт бит 15 (`shl bp,1`), декод позиции — байт из бит 16-23 (`shl ebp,8`).
Верный порт — в [`../tools/lzhuf.py`](../tools/lzhuf.py) (register-faithful,
проверен рендером экрана «Опции» и спрайтов).

Ключевые моменты:

- битовый читатель — **MSB-first**, окно 16 бит (эквивалент NGI-версии с
  32-битным аккумулятором и сдвигом `bp`);
- `DecodeChar`: спуск по дереву от `son[R]`, добавляя биты, пока `c < T`;
  затем `c −= T`, обновление частот (`update`);
- при `c < 256` — литерал; иначе длина `= c − 253`, позиция через `DecodePosition`
  (старший байт → `d_code`/`d_len`, затем добор битов);
- кольцевой буфер предзаполнен `0x20`, запись с `0xFC4`.

Проверка корректности — палитра `ARRI0001.COL` (1024 = 256×RGBA):
декодируется в чистые RGBA-группы с серым градиентом
`(9,9,9,0) (18,18,18,0) (26,26,26,0) …`, каждый 4-й байт `= 0`, энтропия 5.08.
Массовый прогон: 2058 записей распакованы без ошибок.

> `.SCR` (скрипты роликов) тоже метод `0x80`, но это **бинарный** формат —
> распаковывается корректно, но не является текстом (см.
> [04-script-language.md](04-script-language.md)).

## Метод `0x100` — raw DEFLATE

227 записей (220 `NGB`, 6 `COL`, 1 `TXT`; в основном интерьеры `HOUSE.DAT` и
карты). Это **стандартный DEFLATE** (RFC 1951) без zlib-обёртки. Обработчик
`sub_238C6` → `sub_26C30` разбирает 2-битный тип блока и вызывает: `0`→
`sub_26440` (stored), `1`→`sub_265B0` (fixed Huffman), `2`→`sub_26720` (dynamic
Huffman: читает `HLIT=257+5бит`, `HDIST=1+5бит`, `HCLEN=4+4бит`, длины кодов —
всё как в DEFLATE). Окно 64 КБ (буфер `0x10000` в структуре `0x10028`).

Реализация тривиальна: Python `zlib.decompressobj(-15)`, Go `compress/flate`.
Проверено: все 227 записей распакованы без ошибок. **Общая декодируемость — 100 %.**

## Сводка адресов (`NGI32.DLL`, ImageBase `0x10000000`)

| Адрес | Функция |
|---|---|
| `0x235D0` | `ngiUnpack` (экспорт, обёртка) |
| `0x23740` | ядро распаковки, диспетчер методов |
| `0x232EF` | проверка магии `NL`, начало NL-загрузчика |
| `0x2333B` | расшифровка директории (потоковый шифр) |
| `0x233B9` | сборка рантайм-структуры `RsLi` |
| `0x26F4E` | общий декомпрессор LZSS / LZHUF |
| `0x26D00` | `StartHuff` (инициализация дерева) |
| `0x26DCE` | `DecodeChar` (символ Хаффмана) |
| `0x26C30` | декомпрессор метода `0x100` (не разобран) |
| `0x23A10` | таблица переходов методов |
